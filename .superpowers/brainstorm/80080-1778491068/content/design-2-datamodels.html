Design — Section 2: Data Models

New entities and extended fields for each feature

1. SuspendedSale — NEW entity

Persists a POS cart so it can be resumed from any terminal. Auto-expires after 7 days.

suspended_sales table
idUUIDPK
tenant_idUUIDNOT NULL, INDEX
refVARCHARe.g. HOLD-000042
terminal_idUUIDwhere it was suspended
user_idUUIDcashier who suspended
customer_idUUIDnullable
warehouse_idUUIDnullable
linesJSONB/TEXTcart line items
discount_typeVARCHARPERCENTAGE / FIXED
discount_valueDECIMAL
tax_methodVARCHARINCLUSIVE / EXCLUSIVE
notesVARCHAR
expires_atTIMESTAMPcreated_at + 7 days
statusVARCHAROPEN / RESUMED / EXPIRED
created_at / updated_atTIMESTAMP

2. PurchaseLine — EXTEND existing entity

Add 2 columns to support partial receiving.

New columns on purchase_lines
received_qtyDECIMALDEFAULT 0, tracks partial receive
received_atTIMESTAMPnullable, set on last receive

Existing columns remain: id, purchase_id, product_id, variant_id, qty, unit_cost, tax_rate, line_total

3. PurchaseReturn — EXTENDED (no schema change)

Existing entity already covers the needs. We're just adding list/search API endpoints — no new columns needed.

Existing fields: id, ref, purchaseId, supplierId, warehouseId, date, status (PENDING/COMPLETED/CANCELLED), lines[], grandTotal, notes

4. Supplier Payments — NEW read-only view

No new table. A composite query across existing payments + purchases + suppliers to build a supplier payment ledger.

SupplierPaymentDto (projection, not entity)
paymentIdUUID
supplierId / supplierNameUUID / String
purchaseRef / purchaseIdString / UUID
amountBigDecimal
methodCASH / BANK_TRANSFER / MOBILE_MONEY...
referenceString (cheque no, transaction ID)
dateInstant
accountId / accountNameUUID / String (paid from)

Data models look right? The key decisions: SuspendedSale is a new table, PurchaseLine gets 2 columns for partial receiving, Supplier Payments is a read-only projection.
