Design — Section 3: API Endpoints

REST endpoints following existing patterns in the codebase

1. Suspended Sales — /api/v1/suspended-sales

SuspendedSaleController (sales-service)
MethodPathAuthDescription
POST / pos.checkout Suspend current cart. Body: lines[], customerId?, warehouseId?, discount*, taxMethod, notes?
GET /?page&size&sort&search sales.view Paginated list with search on ref, terminal, user, customer
GET /{id} sales.view Single suspended sale detail with full lines
POST /{id}/resume pos.checkout Resume into POS cart. Returns full cart payload. Sets status=RESUMED.
DELETE /{id} sales.manage Discard a suspended sale (single)
DELETE /expired sales.manage Purge all expired holds (called by scheduler or admin)

2. Goods Received — /api/v1/purchases (extend)

New endpoints on PurchaseController
MethodPathAuthDescription
GET /receiving?page&size&supplierId&from&to purchase.view List received/partially-received purchases with receivedQty per line
POST /{id}/receive-line purchase.manage Record received quantity for a line. Body: {lineId, receivedQty}. Auto-sets status=RECEIVED when all lines fulfilled.

3. Supplier Returns — /api/v1/purchase-returns (extend)

New endpoints on PurchaseReturnController
MethodPathAuthDescription
GET /?page&size&status&supplierId&from&to&search purchase.view Paginated list with filters (was only create before)
POST /{id}/complete purchase.manage Mark return as COMPLETED (status transition from PENDING)

4. Supplier Payments — /api/v1/payments/supplier (new)

SupplierPaymentController (payment-service)
MethodPathAuthDescription
GET /?page&size&supplierId&from&to&method&search payment.view Paginated list of all supplier payments across purchases
GET /{supplierId}/ledger?from&to payment.view Supplier ledger: purchases (debits) + payments (credits) + outstanding balance

All endpoints follow the same conventions as existing controllers (pagination, tenant scoping, Cacheable annotations, PreAuthorize guards). Does this API surface cover what's needed?
