Which PDF generation approach should we use?

The codebase already has two patterns. We need to pick one as the foundation for the entire Document & Print system.

A

HTML/CSS → Browser Print (Frontend)

Same pattern as Receipt.tsx and PrintLabelsPage.tsx today. React components render HTML, inject into DOM, call window.print(). Zero backend PDF generation needed.

Pros

  • No new backend code
  • Designers can style with CSS
  • Instant preview in browser
  • Works offline
  • Already proven in the app

Cons

  • No server-side PDF for email/WhatsApp
  • Depends on browser print dialog
  • Inconsistent across browsers
  • No background/bulk generation
  • Hard to version/archive server-side
B

OpenPDF (Backend Java)

Same pattern as InvoicePdfGenerator.java and PdfExporter.java. Pure Java PDF generation using OpenPDF library. Programmatic, no templates.

Pros

  • Server-side PDF = email/WhatsApp ready
  • Consistent output everywhere
  • Background/bulk generation
  • Already proven in backend

Cons

  • Very labor-intensive for rich layouts
  • Designers can't touch it
  • Each template = Java code
  • Hard to customize per tenant
  • OpenPDF has limited CSS support
C

HTML → PDF Engine (WeasyPrint / Gotenberg)

A dedicated HTML-to-PDF microservice. Templates are HTML/CSS files. Backend renders HTML with data, sends to engine, gets PDF back. Store in MinIO.

Pros

  • Beautiful CSS-styled PDFs
  • Designers can edit templates
  • Server-side = email/WhatsApp
  • Bulk generation supported
  • Same templates for preview & PDF
  • Industry standard (Odoo, ERPNext)

Cons

  • New infrastructure dependency
  • Need to run a sidecar service
  • Learning curve for template syntax
  • ~1-2s per document generation
