Which HTML-to-PDF engine?

This is the rendering heart of the entire system. It determines infrastructure, performance, and what CSS features templates can use.

A

Gotenberg

Docker-based service wrapping Chromium + LibreOffice. Industry standard, used by Odoo and many ERP systems. Converts HTML, Markdown, Office docs → PDF.

Pros

  • Full Chromium rendering = perfect CSS
  • Handles any HTML/CSS/JS
  • Also converts DOCX, XLSX, images
  • Stateless REST API, easy to scale
  • Well-maintained, corporate backing

Cons

  • Requires Docker runtime
  • ~200MB container image
  • Slower cold start (~1-2s per doc)
  • Extra infrastructure to manage
B

WeasyPrint

Python library that implements its own CSS layout engine. No browser dependency. Pure Python, lightweight. Used by ERPNext, InvoicePlane.

Pros

  • No Docker/browser dependency
  • Fast (~200ms per doc)
  • Lightweight (pip install)
  • Great for serverless/embedded
  • Consistent output

Cons

  • Partial CSS support (no Flexbox/Grid well)
  • No JavaScript execution
  • Complex CSS layouts can break
  • Font rendering differs from browsers
  • Limited to HTML → PDF only
C

Headless Chromium (Puppeteer / Playwright)

Spin up headless Chrome/Chromium directly. Your Java backend calls it via subprocess or CDP protocol. Full browser rendering.

Pros

  • Pixel-perfect browser rendering
  • Full CSS Grid, Flexbox, Web Fonts
  • Already have pdfjs-dist in frontend
  • No extra service to manage (if using subprocess)

Cons

  • Heavy memory per instance (~200MB)
  • Need to manage Chrome processes
  • Slower than WeasyPrint
  • Subprocess management = brittle
  • Concurrency needs process pool
